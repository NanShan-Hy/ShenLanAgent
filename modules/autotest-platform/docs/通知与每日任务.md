# 每日任务与通知推送

## 每日回归

TestDock侧栏“定时任务”→新建。默认暂停、北京时间09:00，可选每天/工作日或高级五段Cron；预览未来五次时间后选择套件与1～20个环境，保存并启用。已有计划保持原启用状态。多环境串行执行，所有环境结束后形成一个批次；过去一分钟以上的触发跳过，不补跑，已有排队/运行批次时跳过重叠。暂停、编辑及删除计划不取消已生成的运行，历史批次仍保留。

每个计划可使用项目默认通知规则，或单独选择渠道和结果范围；取消“使用项目默认通知规则”且不选渠道表示关闭该计划推送。通知未配置仍可运行测试，发送端不会凭空生成渠道。默认项目规则仅包含定时触发，手动和CI需管理员选择开启。全部结果包括成功、失败、异常和取消；“仅失败和异常”不包含成功或取消。

## 配置渠道

项目管理员进入“通知推送”。创建渠道、明确接收目标，保存后可“发送测试通知”并在发送记录查看结果，最后核对手机。配置密钥不回显，编辑留空保留原值。新渠道默认关闭，启用代表允许向指定目标发送本项目的结果概要。

- 钉钉企业内部应用：需已发布应用机器人并开通发送权限，填AppKey、AppSecret、robotCode及接收群ID；将机器人加入目标群。robotCode独立填写，不假设等于AppKey。酷应用安装可填写对应编码。令牌按应用缓存，接近有效期刷新。
- 存量Webhook：只接受https://oapi.dingtalk.com/robot/send?access_token=…；根据现有机器人安全设置填写加签密钥和关键词，IP白名单由钉钉后台管理。新接入推荐应用机器人；钉钉官方已提示自定义机器人产品下线安排，参见官方文档。
- 个人微信：使用Server酱Turbo（SCT类型SendKey），先在Server酱后台配置微信接收通道；SC3是独立App，本次不作为微信渠道。当前官方免费额度每天5条，账户具体额度以供应商后台为准；本平台不会自动购买或订阅。一次多环境测试每渠道一条，不逐环境占用消息额度。

官方参考：[钉钉应用群消息](https://open.dingtalk.com/document/development/the-robot-sends-a-group-message.md)、[存量Webhook说明](https://open-dingtalk.github.io/developerpedia/docs/learn/bot/webhook/overview/)、[Server酱接入](https://sct.ftqq.com/docs/integrations/python/)。

## 推送规则与权限

管理员在“项目默认推送规则”选择渠道、触发方式和结果范围。tester可为计划选择本项目已批准渠道；viewer只读。渠道授权责任人为最近保存该渠道的项目管理员；投递前再次检查其账号活跃且仍具项目管理权限。频道关闭、删除或凭据/目标更新后取消待发消息，防止将历史数据自动转给新目标；人工重发会使用当前配置并留下审计记录。

推送只包含项目/计划、各环境结果、用例统计、北京时间、耗时及报告链接，不发送请求响应正文、错误原文、环境变量、截图或Trace。外部群成员由配置人管理，平台不能对外部已收到的消息执行来源撤权；完整报告仍需登录和当前项目权限。report_base_url默认局域网地址，手机在外网时需接入能访问虚拟机的网络；不自动开放公网。

## 发送状态与故障处理

独立testdock-notifier.service处理SQLite持久发件箱，不阻塞测试。测试终态与入队同事务，每批次/渠道最多一个逻辑通知。通知队列不扫描发布前的历史报告；规则在任务提交时取快照，变更影响后续任务。

“渠道已受理”表示供应商返回接受，不代表微信或钉钉已在手机送达、阅读。明确限流或连接前失败按1/5/15分钟最多重试3次；鉴权、参数或额度错误直接失败。发送后超时、请求中断、服务端未知结果或执行器在提交中重启时标“状态未知”，不会自动重发。人工核对接收端后再重发，可能出现重复消息。每个接收目标至少间隔6秒，避免一组渠道阻塞其他目标。

## 接口与数据

旧schedules接口继续支持environment_id；新environment_ids支持多环境，同时提交时首项须一致。notification_channel_ids=null表示继承项目规则、[]表示关闭、非空表示显式渠道；notify_mode=null继承规则，all/failures显式选择。GET会返回规范化列表。

POST /api/projects/{id}/schedules/preview接受cron/timezone并返回未来五次Unix秒。GET /api/projects/{id}/schedule-batches支持page，每页20；GET /api/schedule-batches/{id}鉴权后返回批次及各运行。页面只显示最近20个批次，更早可通过分页接口或批次链接访问。

项目级notification-channels接口支持GET/POST/PUT/DELETE，/{channel}/test用于明确试发；配置JSON为name、kind（dingtalk_app/dingtalk_webhook/serverchan）、credentials和enabled。notification-rules为channel_ids、triggers（schedule/manual/ci）及mode。notification-deliveries按page分页，/{delivery}/retry要求管理员，accepted/sending/pending状态不可重复重发。响应不会返回完整凭据。写操作沿用TestDock请求标识及项目鉴权。

数据库schema2新增批次、渠道、规则、发件箱和尝试记录，旧计划迁移为单环境；实际测试报告保留原结构。通知数据和加密密钥随手动一致性备份保存，资产导出不包含通知凭据。
