# 深蓝智能迁移总手册

本手册面向将当前 Intel Mac 上的 Ubuntu 虚拟机迁移至 Windows/VMware Workstation，或在新 Ubuntu 中重建服务。仓库入口：https://github.com/NanShan-Hy/ShenLanAgent 。实际采集范围、时间见 [machine-state.json](../infra/migration/machine-state.json)。

## 两种迁移方式

### A. 整台虚拟机迁移：保留现有环境

适合保留所有 Linux 软件、配置、账号和业务数据。先在维护窗口停止任务并正常关闭 Ubuntu，不能复制运行中或挂起状态的磁盘。

1. 在 Mac 的 Fusion 中定位该虚拟机的 .vmwarevm 包，复制完整包及全部关联磁盘文件到受控存储；保留原机副本。不能只复制一个 vmdk 描述文件或快照链的一部分。
2. 在 Windows 上使用兼容当前虚拟硬件的 VMware Workstation，打开包内 .vmx。Windows 可能将包显示为普通文件夹。先断开新机虚拟网卡，避免克隆的定时任务、OAuth 刷新和穿透身份同时上线。
3. 为新机分配资源，建议先 4 vCPU、16GB RAM；CPU 型号确认后再调整。虚拟盘扩容与 Ubuntu 的分区/LVM/文件系统扩容分别执行，原根卷约23GiB不会自动变成新容量。
4. 按 VMware 的“移动/复制”提示选择符合实际用途的选项；复制会产生新的虚拟机身份/MAC。核对网卡名、DHCP 地址和默认路由，不能继续假定 ens33 或 172.16.61.128 不变。
5. 按[代理与网络](代理与网络迁移.md)修改 Mac 代理地址、访问隧道和花生壳设备/映射，确认旧机不会重复执行任务后再恢复网络。
6. 执行 scripts/migration/check_services.py；逐项验证业务与定时任务后切换访问入口。新机稳定前保留旧机离线副本，回退前处理新机产生的业务数据。

此方法的虚拟机镜像含真实密钥和业务数据，只通过受控存储传输，不进入公开 GitHub 仓库。

### B. 新 Ubuntu 重建：源码＋私密迁移包

推荐 Ubuntu 24.04 LTS amd64，并创建相同用户 nanshan、沿用 /home/nanshan/workspace。当前模块存在绝对路径配置；更换用户名需同步核对脚本、JSON 和所有 systemd 单元。

```bash
sudo apt update
sudo apt install git curl rsync patch python3-venv python3-dev build-essential nodejs npm openssh-server open-vm-tools fonts-noto-cjk
mkdir -p /home/nanshan/workspace/projects
git clone https://github.com/NanShan-Hy/ShenLanAgent.git /home/nanshan/workspace/projects/shenlan-agent
cd /home/nanshan/workspace/projects/shenlan-agent
python3 scripts/migration/prepare_workspace.py
python3 scripts/migration/prepare_workspace.py --apply
```

prepare_workspace 先显示计划；--apply 只创建目录、复制模块源码，不安装系统包、不写真实密钥、不启动服务；目标模块目录存在时停止，避免覆盖已有项目。

分别为三个模块重建依赖，不能直接复制旧 .venv：

```bash
for module in ai-gateway ai-workbench autotest-platform; do
    python3 -m venv "/home/nanshan/workspace/projects/$module/.venv"
    "/home/nanshan/workspace/projects/$module/.venv/bin/python" -m pip install -r "/home/nanshan/workspace/projects/$module/requirements.lock"
    "/home/nanshan/workspace/projects/$module/.venv/bin/python" -m pip check
done
/home/nanshan/workspace/projects/autotest-platform/.venv/bin/python -m playwright install --with-deps chromium
```

新机若已通过系统安装浏览器依赖，将 TestDock settings.json 中旧 browser_library_path 改为空字符串；旧机使用 tools/playwright-libs/1.2.11 中的单独 libasound，不应假定该路径在新机存在。原包/字体/Go/账号池安装包的路径与 SHA-256 见 [artifacts.json](../infra/migration/artifacts.json)。系统软件清单见 [packages.tsv](../infra/migration/packages.tsv)，该清单用于核对，不是跨版本强制安装全部同版本包的脚本。

## 还原模型与账号池程序

- 复制旧机 workspace/tools/ai-models（含符号链接目标），按 [model-manifest.json](../infra/migration/model-manifest.json)校验；或者运行工作台 scripts/prepare_models.py 下载公开 OCR/嵌入模型。该脚本使用既有 /home/nanshan 路径，联网下载需先配置代理。
- 保留公开模型的模型卡和许可文件；测试语义检索与 OCR，不能仅凭文件存在判定模型可运行。
- 复制 tools/cliproxyapi/8.0.72-gateway.2（程序、LICENSE、release.json），或用网关内固定提交、补丁和校验构建：

```bash
cd /home/nanshan/workspace/projects/ai-gateway
PYTHONPATH=src .venv/bin/python scripts/build_account_pool_adapter.py
```

构建依赖下载指定 Go1.26.10 和固定 CLIProxyAPI SDK；补丁在 bridge/account-binding.patch。必须使用 gateway.2 适配版，普通8.0.72不能替代账号绑定契约。具体上游提交和现有程序哈希见 artifacts.json。构建二进制的校验值与当前备份程序是否一致需要实际核验，不把其他构建环境视为天然逐字节相同。

## 原生工具与宿主机配置交接

以下文件保留软件原生位置，不能为目录整齐搬移。迁移前逐项导出，含凭据的文件只进入私密迁移包：

| 类别 | 原机位置/状态 | 新机处理 |
| --- | --- | --- |
| Shell与代理 | ~/.bashrc、~/.profile、/etc/environment | 合并自己的配置，修改宿主机代理地址；不覆盖新机默认文件 |
| SSH | ~/.ssh/authorized_keys，sshd配置位于/etc/ssh | 原机用户目录只发现authorized_keys；新客户端自行生成密钥并授权，主机密钥保留或重建按实际迁移方式处理 |
| Git/GitHub | 各项目.git；新总仓库已有本地提交 | 原三个仓库历史保留在源机，汇总仓库记录来源基线；新机拉取ShenLanAgent，命令行认证另行登录，不复制Token到仓库 |
| Codex | /usr/local/bin/codex及npm全局安装，~/.codex原生目录 | 版本见infra中的codex-version.txt；新机按所用版本安装并重新登录；config.toml、MCP连接、会话和auth资料按敏感内容单独审核迁移 |
| npm/pip | ~/.npm、~/.npmrc、~/.config/pip、~/.pip（按实际存在项） | 缓存可重建；私有源凭据单独迁移；各模块按requirements.lock重建.venv |
| iKuuuVPN | dpkg 0.18.5+1，/usr/share/iKuuuVPN | 原包已归档；本次未验证其桌面连接，不将其当作当前Mac Clash代理；订阅与登录状态在原客户端单独导出 |
| Chromium/字体 | ~/.cache/ms-playwright、~/.local/share/fonts/testdock-noto-cjk | 按锁定Playwright安装浏览器、系统字体与运行库；可重建缓存，不直接迁移.venv |
| systemd/NTP/网络 | ~/.config/systemd/user、/etc/netplan/50-cloud-init.yaml、systemd-timesyncd | 业务单元已入仓库；新机DHCP/MAC/网卡名重新核对；root级网络及防火墙规则需管理员导出 |
| Mac/Fusion | 用户报告macOS12/Fusion13，配置在宿主机 | VMX/磁盘链、Fusion NAT规则、Clash规则/订阅不在Linux内，整机复制与宿主机导出分别办理 |
| 花生壳云端 | 本人贝锐账号、设备与映射 | 云端映射不能由本机进程列表还原，在厂商控制台导出/记录并在外网复测 |

不恢复整套历史缓存也可以重建环境；真实配置、配套密钥和数据库是保留业务的必要输入。新机接电并配置合适的睡眠/开机策略，Windows睡眠会使来宾服务不可用；实际开机自启需另行测试宿主机与VMware启动流程。

## 私密迁移包：保留账号、历史和配置

GitHub 只包含源码与去敏模板。要保留账号、报告、模型配置、钱包/账本、历史会话和授权，必须另带以下内容：

| 必须配套迁移 | 来源 |
| --- | --- |
| 三个业务服务真实配置、master.key及数据 | workspace/services/{ai-gateway,ai-workbench,autotest-platform}/{config,data} |
| GPT账号池内部管理/调用Key、代理与OAuth授权 | workspace/services/gpt-account-pool/{config,data} |
| 桥接密钥 | TestDock config/ai-bridge.key 与工作台 config/testdock-bridge.key，必须配套 |
| 公开模型、账号池适配程序、必要安装包 | workspace/tools/ai-models、tools/cliproxyapi/8.0.72-gateway.2、downloads/installers |
| 花生壳设备状态 | /etc/phtunnel.json，需管理员权限和停机复制；或在新机重新激活绑定 |
| 登录与远程访问 | 迁移自己的 SSH 公钥授权及按需重建客户端隧道，不共享私钥 |

准确切换时点需要先暂停生产计划并等待测试、通知和网关请求结束，再停止下列10个业务单元。以下命令仅供计划维护窗口使用，本次编写文档时未停服：

```bash
systemctl --user stop testdock-ai-worker testdock-worker testdock-notifier testdock testdock-demo-dev testdock-demo-test ai-workbench-worker ai-workbench ai-gateway gpt-account-pool
```

停写后，将上述4个服务的 config/data 保存到 workspace/backups/shenlan-migration/独立UTC快照，目录700、文件600；用 tar 保留相对路径并生成 SHA-256。如使用 GnuPG：

```bash
# snapshot_dir 必须指向已新建的独立、权限700目录；同名归档存在时停止。
snapshot_dir='/home/nanshan/workspace/backups/shenlan-migration/替换为UTC快照'
( set -o noclobber; tar -C /home/nanshan/workspace -cf "$snapshot_dir/services-private.tar" services/ai-gateway/config services/ai-gateway/data services/ai-workbench/config services/ai-workbench/data services/autotest-platform/config services/autotest-platform/data services/gpt-account-pool/config services/gpt-account-pool/data )
chmod 600 "$snapshot_dir/services-private.tar"
gpg --symmetric --cipher-algo AES256 --output "$snapshot_dir/services-private.tar.gpg" "$snapshot_dir/services-private.tar"
sha256sum "$snapshot_dir/services-private.tar.gpg" > "$snapshot_dir/services-private.tar.gpg.sha256"
```

加密归档也保存在仓库外，口令通过本人受控渠道保管；明文归档不自动清理。系统级花生壳配置需管理员另行安全导出，不能把 SN/口令打印进公开日志。恢复时校验、先解包到独立临时目录检查，再放入新机服务目录；配置/数据目录700、秘密文件600，归属新机运行用户。数据库先做只读 integrity_check，并检查配套密钥能解密。

各模块现有备份/verify工具用于隔离恢复验收，会暂停计划、关闭账号/模型或更换内部连接信息；不要把经去授权处理的验证副本当作未经处理的生产迁移包。正式启用哪些计划、渠道、账号和模型，须按当前权限与新环境逐项核对。

## 安装单元与上线

在还原真实配置、数据库、模型和账号池程序之后，准备 app 程序副本：将各模块源码（不含 .git/.venv/缓存）放入对应 services/<模块名>/app，按各模块部署脚本核验版本和数据 schema。若跨版本升级，先备份并执行模块要求的显式迁移，不能跳过。

```bash
install -d -m 700 ~/.config/systemd/user
cp /home/nanshan/workspace/projects/shenlan-agent/infra/migration/systemd-user/* ~/.config/systemd/user/
systemctl --user daemon-reload
sudo loginctl enable-linger nanshan
# 配置、数据与 app 就绪之后再启动：
systemctl --user enable --now gpt-account-pool ai-gateway ai-workbench ai-workbench-worker testdock testdock-worker testdock-notifier testdock-ai-worker testdock-demo-dev testdock-demo-test
python3 /home/nanshan/workspace/projects/shenlan-agent/scripts/migration/check_services.py
```

模板保留旧机资源限额（网关384MiB、账号池256MiB、工作台合计1280MiB/1核等）；新虚拟机变大不会自动放宽应用限额，按实际负载另行调整。不会因为单元启用就声称重启/注销已实测：新机应在计划窗口分别测试，保留检查结果。

## 验收与切换

- 系统：IP/DNS/NTP、磁盘余量、权限、SSH、用户级systemd和Linger。
- 应用：健康接口、worker/notifier/AI worker心跳、管理员登录、旧资产与历史报告、配套密钥解密和账本一致。
- 模型：账号池在线、原应用Key与模型范围、授权有效；真实模型试调用单独确认，未知旧请求不重放。
- 联动：TestDock→工作台知识权限与网关连接、附件/会话访问、计划与通知接收人。
- 网络：宿主机HTTP代理可达、隧道/HTTPS访问、花生壳控制台在线和真实外网映射。
- 整机：重启/注销后重新检查；旧机保持离线，避免两个实例重复执行任务或同时刷新账号。

当前只完成原机只读采集与发布内容校验；Windows新宿主机、整机搬迁、外网映射以及新机重启恢复均需迁移后实测。
